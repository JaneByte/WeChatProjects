## 一、替换 `5.4 本章小结`

本章围绕系统实现过程进行了说明，分别从用户端和管理端两个方面介绍了主要功能模块的实现思路。用户端已实现首页导购、分类浏览、搜索、商品详情、购物车、订单结算、订单查询、地址管理、优惠券领取与查看、个人中心、小份优选、场景搭配、时令推荐、评价与售后信息查看等核心能力；管理端已实现后台登录、经营概览、店铺信息维护、商品管理、分类管理、订单管理、优惠券模板管理、方案规则配置与运营配置维护等后台能力。

从实现完整性看，系统模块已覆盖“浏览—选购—结算—履约—反馈—配置”的业务闭环。前台侧重用户交互与交易流程组织，后台侧重数据维护、状态处理与运营策略配置，后端负责鉴权、规则计算、订单状态流转和数据一致性控制，数据库提供统一持久化支撑。前后台共用同一业务服务和数据源，能够保证配置调整、商品状态与交易结果在两端一致生效。

需要强调的是，本系统并非仅实现基础商城能力，还实现了“场景化选购 + 配置化运营”的特色链路：用户端推荐结果可直接进入交易链路，管理端策略调整可反向影响推荐与展示。基于以上实现，本论文第六章进一步采用覆盖矩阵、边界与异常用例、状态流转用例和一致性校验用例对系统进行验证，确保“实现内容”与“测试内容”形成完整闭环。

## 6 系统测试

系统测试的目标是验证各功能模块在真实运行环境下是否满足设计要求，并重点检验前端页面、后端接口与数据库状态之间的一致性。考虑到系统由微信小程序用户端、Web 管理端、Spring Boot 后端服务和 MySQL 数据库组成，本章测试不仅关注页面可用性，还覆盖交易链路正确性、配置生效正确性、状态流转合法性与关键数据一致性。

与“仅验证页面是否可打开”的浅层测试不同，本章采用“覆盖矩阵 + 验证型用例 + 量化统计”的测试方法：先建立功能覆盖映射，再针对高风险链路设计边界、异常、权限和状态流转测试，最后按统一口径汇总执行结果，提升测试结论的可复核性和说服力。

### 6.3 测试用例设计方法

本章用例设计采用以下方法，确保测试不止停留在“功能可点击”层面。

1. 等价类划分：对登录、搜索、地址、优惠券门槛、推荐参数等输入进行有效/无效分类。
2. 边界值分析：对数量、库存、金额门槛、折扣上下限、时令权重等设置边界值。
3. 状态迁移测试：对订单状态、退款状态、优惠券状态进行合法/非法流转校验。
4. 异常路径测试：对无效 Token、商品下架、规格停用、库存不足、重复提交进行校验。
5. 一致性测试：核对页面结果、接口响应与数据库落库结果是否一致。

### 6.6 测试结果分析

综合本章测试结果可知，系统在基础交易链路、后台维护链路和特色推荐链路上均具备可运行性。用户端能够完成浏览、搜索、加购、下单、支付、订单跟踪与信息维护；管理端能够完成商品、分类、订单、优惠券及配置项维护，并对前台展示与推荐结果产生联动影响。

在高风险链路方面，订单状态流转、库存扣减、优惠券核销与回滚、规则配置生效和权限控制均得到针对性验证，说明系统已从“页面可用”提升到“业务可验证、数据可校验”的质量层级。通过覆盖矩阵可确认，测试范围已与第五章实现模块建立一一映射关系，避免了“实现有描述、测试无验证”的断层问题。

仍需说明的是，本章测试以功能正确性与一致性为主，性能压测、长稳测试和安全渗透测试尚未系统展开。若后续面向更大规模上线，应继续补充并发压测、接口限流、审计日志与安全加固等专项测试。
